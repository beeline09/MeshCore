# MCOa compatibility pack

Публичная South Edition распознаёт форматы MeshCore Open Advanced, не меняя
их радиоформат и не скрывая binary-data от подключённого клиента.

## Возможности

- MCOtxt: декодирование `mct:` и binary envelope `0x0120/0x3*` для каналов и
  личных сообщений.
- MCMP: определение текстовых `mcmp:`, `mcmp2:`, `mcmp3:` и binary envelope
  `0x0120/0x2*`; вместо сжатого текста показывается `<MCMP vN message>` или
  `<MCMP vN signed message>`.
- AEIC: определение чанков `0xAE1C`; один раз на поток картинки показывается
  `<AEIC image>`.
- MCOimg: определение `im:`, `imN:` и binary envelope `0x0120/0x1*` без
  декодирования картинки; показывается `<MCOimg vN image>` (для старого `im:` —
  `<MCOimg image>`).

Все четыре опции по умолчанию включены. Выключение прекращает преобразование и
показ заглушек, но не блокирует и не изменяет исходный пакет.

## Совместимость с приложениями

При подключении приложение отправляет прошивке `CMD_APP_START` со строкой вида:

```text
MeshCoreOpen;cap=mctxt,mcmp,mcimg,aeic
```

Возможности перечисляются через запятую в одном поле `cap=`. Если capability
объявлена, приложение получает исходный формат без дополнительной текстовой
заглушки. Для AEIC имя приложения `MeshCoreOpen` (без учёта регистра и
разделителей) также считается признаком поддержки.

Offline-очередь всегда хранит исходные companion-кадры. Декодирование и
подстановка заглушек выполняются только при `CMD_SYNC_NEXT_MESSAGE`, с учётом
capability текущего подключённого клиента. Поэтому накопленные кадры не
зависят от того, какое приложение было подключено в момент их приёма. Если
преобразованное MCOtxt-сообщение разбивается на части или для binary-формата
создаётся заглушка, эти производные кадры не добавляются в offline-очередь и
не вытесняют из неё другие сообщения: в очереди остаётся ровно один исходный
кадр каждого сообщения. Для binary MCOimg, MCMP и AEIC при синхронизации
сначала отдаётся этот исходный кадр, а затем при необходимости на лету
формируется и отдаётся текстовая заглушка. Признак AEIC хранится как флаг в
записи исходного кадра, а не как отдельный элемент очереди. Локальный экран от
companion-очереди не зависит: для него сообщение преобразуется сразу при
приёме. Если поддержки нет:

- все binary-форматы (MCOtxt, MCMP, AEIC и MCOimg) сначала отдаются клиенту
  как исходные binary-data; для MCOtxt следом выдаётся декодированный обычный
  текст. Если он не помещается в один companion-кадр, он делится по границам
  UTF-8 на видимые части вида `Sender: текст [1/2]`,
  `Sender: ...продолжение [2/2]`; для остальных форматов рядом добавляется
  текстовая заглушка;
- в `group_text` корректно распознанные Base91-представления `mct:`,
  `mcmp*:` и `im*:` преобразуются непосредственно внутри исходного сообщения:
  MCOtxt-фрагмент заменяется декодированным текстом, а MCMP/MCOimg —
  соответствующей заглушкой. Имя отправителя, reply-упоминание и окружающий
  обычный текст сохраняются. Например,
  `Sender: @[Name] смотри im4:... как тебе?` превращается в
  `Sender: @[Name] смотри <MCOimg v4 image> как тебе?`. Несколько фрагментов
  в одном сообщении обрабатываются последовательно. Клиент с соответствующей
  capability получает исходный `group_text` без преобразования. AEIC не имеет
  текстового транспорта:
  изображения этого формата по-прежнему распознаются по binary-чанкам `0xAE1C`.

## Настройки и TerminalCLI

В Settings доступны `MCOtxt`, `MCMP detect`, `AEIC detect`, `MCOimg detect`.

```text
get mcotxt
set mcotxt on|off
get mcmp.detect
set mcmp.detect on|off
get aeic.detect
set aeic.detect on|off
get mcoimg.detect
set mcoimg.detect on|off
```

Настройки сохраняются в `ui`-группе prefs. Соответствующие compile-time флаги:

```text
WITH_MCOTXT
WITH_MCMP_DETECT
WITH_AEIC_DETECT
WITH_MCOIMG_DETECT
```
