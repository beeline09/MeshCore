# Роль ping_bot — ответ маршрутом на «ping» в хештег-группе

Нода слушает хештег-группу (по умолчанию `#ping`) и на сообщение `ping` отвечает в ту же
группу, показывая путь, которым пакет до неё добрался.

## Формат ответа

```
@Vasya
Sever-Rep[025d]
a1
Dom-2[998a]
-3 hops
```

- Первая строка — `@` и имя отправителя, взятое из префикса `"Имя: "` входящего текста.
- Дальше по строке на ретранслятор, **от бота назад к пользователю**: последняя строка —
  репитер, услышавший отправителя первым.
- Имя подставляется, только если префикс хеша однозначно резолвится среди контактов-репитеров.
  Иначе печатается hex в нижнем регистре.
- Последняя строка — `-N hops`, где N всегда настоящее число хопов. При нуле хопов список
  репитеров пуст, а хвост становится `-0 hops - Direct` — бот услышал отправителя напрямую:

```
@Vasya
-0 hops - Direct
```

- Слово-триггер сравнивается без учёта регистра, так что подходят и `ping`, и `PING`, и `pING`.

### Лесенка деградации

Ответ ограничен `PING_BOT_MAX_MSG_LEN`. Форматы пробуются по порядку, берётся первый,
который влезает:

| # | Вид | Примерная ёмкость |
|---|-----|-------------------|
| 1 | `Имя[hex]` построчно | ~8 хопов |
| 2 | `Имя` построчно | ~13 хопов |
| 3 | `hex, hex, hex` одной строкой | ~20 хопов |
| 4 | то же с минимальной элизией: `hex, ..., hex` | всегда |

Выбрасывается из середины ровно столько записей, сколько не влезает; остаток делится
симметрично, чтобы оба конца маршрута остались видны.

## Почему нужен хук logRx

`Packet::calculatePacketHash()` считает хеш по типу и payload, **без `path`**. Значит копии
одного сообщения, пришедшие разными маршрутами, имеют одинаковый хеш и отсекаются в
`hasSeen()` (`Mesh.cpp`, ветка `PAYLOAD_TYPE_GRP_TXT`) ещё до расшифровки канала. До
`onChannelMessageRecv()` доезжает только **первая** копия — не обязательно кратчайшая,
о чём в коде есть прямой комментарий «first packet wins».

Поэтому выбор кратчайшего маршрута устроен так:

1. `onChannelMessageRecv()` ловит триггер, запоминает хеш пакета и открывает окно сбора.
2. `logRx()` — хук `Dispatcher`, который вызывается для каждого принятого пакета **до**
   дедупликации, — в течение окна подкладывает копии с тем же хешем.
3. По истечении окна выбирается вариант с минимальным hop count и отправляется ответ.

Пауза перед ответом заодно разводит бота с чужим трафиком в эфире.

## Дефайны

| Дефайн | Смысл | Дефолт |
|--------|-------|--------|
| `WITH_PING_BOT` | включает роль | — |
| `PING_BOT_NAME` | имя ноды при первом старте | `"PingBot"` |
| `PING_BOT_GROUP` | имя хештег-группы **без** `#` | `"ping"` |
| `PING_BOT_REGION` | регион (transport scope) для ответа, **без** `#`; `"*"` = без региона | `"*"` |
| `PING_BOT_MAX_MSG_LEN` | полный лимит сообщения | `155` |
| `PING_BOT_TRIGGER` | слово-триггер | `"ping"` |
| `PING_BOT_WINDOW_MS` | окно сбора маршрутов | `8000` |
| `PING_BOT_COOLDOWN_SEC` | пауза на одного отправителя | `300` |
| `PING_BOT_MAX_PER_HOUR` | потолок ответов в час | `30` |

`PING_BOT_MAX_MSG_LEN` — это **полный** размер вместе с префиксом `"<имя ноды>: "`, который
`sendGroupMessage()` подставляет сам и считает против того же лимита. Жёсткий потолок
прошивки — `MAX_TEXT_LEN` (160), и выход за него обрезается **молча**, срезая именно хвост
`-N hops`. Поэтому длина считается до отправки, а дефайны проверяются на этапе компиляции:

```
examples/companion_radio/PingBot.h:45:4: error: #error "PING_BOT_MAX_MSG_LEN exceeds
MAX_TEXT_LEN (160). sendGroupMessage() would silently truncate the reply and cut off the
trailing '-N hops' line. Lower PING_BOT_MAX_MSG_LEN to 160 or less."
```

Проверяются также пустые и слишком длинные `PING_BOT_NAME` / `PING_BOT_GROUP`, `#` в начале
имени группы и диапазон `PING_BOT_WINDOW_MS`.

Ключ хештег-группы — первые 16 байт `sha256("#" PING_BOT_GROUP)`. Канал регистрируется при
старте в первый свободный слот по образцу служебного `TerminalCLI`.

`PING_BOT_NAME` работает как `ADVERT_NAME`: задаёт имя только при первом старте, дальше имя
живёт в prefs и меняется через CLI или приложение.

## Настройки ноды-бота

Автодобавление контактов ограничено репитерами (`manual_add_contacts = 1`,
`autoadd_config = AUTO_ADD_REPEATER | AUTO_ADD_OVERWRITE_OLDEST`) — в ответе фигурируют
только они, тратить слоты на остальные типы незачем.

`MAX_CONTACTS` поднят с 350 до 500. Освободить бюджет помогли `OFFLINE_QUEUE_SIZE` (256 → 16:
боту не нужна очередь сообщений для приложения) и `MAX_GROUP_CHANNELS` (40 → 8: нужно 3 слота —
Public, TerminalCLI, `#ping`).

Ограничение сверху даёт не RAM, а flash: контакты лежат в `ExtraFS` (100 КБ) по ~151 байту
на запись, то есть 500 контактов занимают ~75 КБ.

## Env

Роль живёт внутри `examples/companion_radio` под `#ifdef WITH_PING_BOT` — ей нужен весь
companion-стек: каналы, база контактов для резолва имён, дисплей, CLI.

«Базовая роль» выражена секцией `[FaketecMiniX_ping_bot]`, от которой наследуются транспортные
env. Для nRF52 (nice!nano) WiFi-варианта нет физически.

| Env | Транспорт | RAM | Flash |
|-----|-----------|-----|-------|
| `FaketecMiniX_ping_bot_usb` | USB CDC | 60.1% | 64.0% |
| `FaketecMiniX_ping_bot_ble` | BLE | 62.0% | 64.8% |

## Попутный фикс: joystick_down

Коммит `f0ff43d6` добавил в общий `ui-new/UITask.cpp` безусловное использование кнопки
`joystick_down`, объявив её только в варианте `promicro_eink_spi`. Этот вариант позже исчез
(остался `promicro_eink_spi_v2` без джойстика), и `joystick_down` не объявлен теперь **нигде** —
из-за чего не собирался ни один вариант с `UI_HAS_JOYSTICK`, включая штатный
`FaketecMiniX_companion_radio_usb`.

Кнопка DOWN сделана опциональной через `UI_HAS_JOYSTICK_DOWN`. Ни один вариант её сейчас не
объявляет, так что все платы с джойстиком возвращаются к раскладке из четырёх кнопок, которая
у них физически и есть.
