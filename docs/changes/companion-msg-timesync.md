# Синхронизация времени companion через таймстемпы сообщений

## Проблема

Companion уже синхронизировал время через advert-таймстемпы. Однако advert-пакеты рассылаются
периодически и редко — начальная синхронизация требует нескольких минут ожидания.

Входящие личные и публичные сообщения содержат таймстемп отправителя, но он использовался
только для отображения — в кворумный буфер не поступал.

## Решение

Добавлен метод `feedMsgTimestamp()`, который подаёт таймстемп из входящего сообщения
в тот же кворумный буфер `_ts_buf`, что и advert-таймстемпы. Вызывается из обработчиков
трёх типов входящих сообщений.

```
onMessageRecv()          → feedMsgTimestamp() → _ts_buf → tryTimeSyncFromBuf()
onSignedMessageRecv()    → feedMsgTimestamp() → _ts_buf → tryTimeSyncFromBuf()
onChannelMessageRecv()   → feedMsgTimestamp() → _ts_buf → tryTimeSyncFromBuf()
```

## Почему это безопасно

Таймстемп сообщения находится внутри зашифрованного payload (ECDH для личных, AES для групповых).
Принять его можно только расшифровав — т.е. он пришёл от авторизованного отправителя.
Одиночный выброс (например, отправитель с неверными часами) не может сдвинуть время —
кворумный алгоритм требует согласия большинства.

Остаточные угрозы и защита:

| Угроза | Защита |
|---|---|
| Старое сообщение из офлайн-очереди | После первой синхронизации: отклонение при расхождении ≥ `MAX_JUMP` (10 часов) |
| Отправитель с намеренно неверными часами | Кворум — одиночный выброс не достигает порога |
| Применение поверх времени от приложения | Проверка `hasRecentAppTimeSet()` — holdoff 6 часов после `CMD_SET_DEVICE_TIME` |
| Таймстемп вне допустимого диапазона | Проверка `MIN_VALID_TS` / `MAX_VALID_TS` (2020–2050) |

## Преимущества

- **Быстрый bootstrap**: в активной сети несколько входящих сообщений могут дать кворум 3/5
  значительно быстрее, чем ожидание advert-пакетов.
- **Групповые каналы**: сообщения из паблик-каналов приходят от независимых пользователей
  с независимыми часами — сильный сигнал синхронизации.
- **Нет дублирования логики**: `feedMsgTimestamp()` использует уже существующий
  `tryTimeSyncFromBuf()` без изменений.

## Логика `feedMsgTimestamp()`

```cpp
void MyMesh::feedMsgTimestamp(uint32_t timestamp) {
  // 1. Диапазон 2020–2050
  if (timestamp <= MIN_VALID_TS || timestamp >= MAX_VALID_TS) return;

  // 2. Holdoff после CMD_SET_DEVICE_TIME
  if (hasRecentAppTimeSet()) return;

  // 3. После первой синхронизации: отклонять таймстемпы старше 10 часов
  if (_ts_sync_count > 0) {
    uint32_t diff = abs_diff(timestamp, getRTCClock()->getCurrentTime());
    if (diff >= MAX_JUMP) return;
  }

  // Добавить в буфер и попробовать синхронизироваться
  _ts_buf[_ts_buf_pos] = { timestamp, 0 };
  _ts_buf_pos = (_ts_buf_pos + 1) % 10;
  if (_ts_buf_count < 10) _ts_buf_count++;
  tryTimeSyncFromBuf();
}
```

Поле `pub_hash` равно `0` — у сообщений нет отдельного идентификатора источника,
пригодного для дедупликации на уровне буфера. Дедупликация обеспечивается кворумным алгоритмом.

## Отличие от advert-таймстемпов

| Свойство | Advert | Сообщение |
|---|---|---|
| Криптографическая подпись | ✅ Ed25519 | ❌ (ECDH/AES шифрование) |
| Гарантия свежести | ✅ Высокая | ⚠️ Средняя (мог быть составлен заранее) |
| Дополнительная защита | — | Проверка отклонения ≥ MAX\_JUMP |
| Счётчики `_ts_advert_count` / `_ts_valid_count` | Обновляются | Не обновляются |
